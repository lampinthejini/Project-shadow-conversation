이 문서의 원칙은 다음과 같다.

- 측정하지 않은 값은 "미검증"으로 둔다. 추정값을 적지 않는다.
- 기준 PC는 집 PC다(AMD RX 9070 XT 16GB). 작업 PC(GTX 1660 Super 6GB)에서 잰 값은 도구 시험과 참고용이며, 0단계 통과 판단에 쓰지 않는다.
- GPU 벤더를 전제하지 않는다. 서빙 엔진 후보는 AMD와 NVIDIA에서 모두 돌아야 한다.
- 측정 입력은 가상의 인물과 상황으로 만든 대역 데이터만 쓴다. 생성 문장은 저장하지 않고 수치만 남긴다.
- 외부 네트워크는 모델과 패키지를 내려받을 때만 쓴다. 측정 중 요청은 localhost로만 간다.

## 3. 사전 준비

1. 집 PC에서 저장소를 받고 Python 3.10 이상을 확인한다. 측정 도구는 표준 라이브러리만 쓴다.
2. 다른 GPU 사용 프로그램(게임, 브라우저 하드웨어 가속 영상 등)을 끈다. S0-11만 예외다.
3. 서빙 엔진을 설치한다. 1차 후보는 아래 두 가지다. 둘 다 AMD·NVIDIA를 지원한다고 알려져 있지만, RX 9070 XT(RDNA4)에서 GPU로 도는지는 미검증이다.

| 후보 | 비고 |
| --- | --- |
| Ollama | 작업 PC에 0.40.18 설치됨. 네이티브 API가 프롬프트 처리 시간·생성 시간을 따로 준다. 병렬 처리는 `OLLAMA_NUM_PARALLEL`로 정한다 |
| llama.cpp server | Vulkan·ROCm·CUDA 빌드가 있다. OpenAI 호환 API로 잰다(`--api openai`). `-c`(컨텍스트)와 `-np`(병렬 슬롯)를 실행 옵션으로 정한다 |

4. 모델은 EXAONE 3.5 7.8B Q4_K_M을 1차로 쓴다. 내려받기 전에 S0-13의 라이선스 원문을 먼저 읽는다.

## 4. 실험 절차

### 집 PC 한 번에 실행

S0-01과 S0-03~05는 스크립트 하나로 돌린다. 모델을 받기 전에 S0-13(라이선스)을 먼저 확인한다.

```
ollama pull exaone3.5:7.8b
powershell -ExecutionPolicy Bypass -File tools\stage0
un_home.ps1
```

- 실행 중인 Ollama(트레이 앱 포함)를 끄고, 병렬 슬롯 1개와 2개로 차례로 다시 띄워 잰다. 끝나면 트레이 앱은 꺼진 채로 둔다.
- 중간에 VRAM을 손으로 적으라는 안내가 두 번 나온다(S0-02).
- 아래 절차는 스크립트가 하는 일을 실험별로 풀어 쓴 것이다. 하나만 다시 잴 때 쓴다.


### S0-01 환경 기록

```
python tools/stage0/env_info.py
```

- OS, CPU, RAM, GPU 이름을 자동으로 기록한다. NVIDIA가 아니면 VRAM 총량은 자동으로 읽지 않으므로 작업 관리자(성능 → GPU → 전용 GPU 메모리)의 값을 손으로 적는다.
- GPU 드라이버 버전, 서빙 엔진 버전, 전원 설정(고성능 여부)도 적는다.

### S0-02 적재·VRAM

1. 엔진을 띄우고 모델을 한 번 불러온다.
2. 아래 값을 기록한다.
   - 유휴 VRAM(모델 적재 전)
   - 모델 적재 직후 VRAM
   - 16K 컨텍스트로 한 번 생성한 뒤 VRAM
   - 병렬 슬롯 2개 설정에서의 VRAM. 슬롯마다 KV 캐시를 따로 잡는 엔진이 있어 S0-05와 함께 본다.
3. 모델이 전부 GPU에 올라갔는지 확인한다. Ollama는 `ollama ps`의 PROCESSOR 열이 `100% GPU`여야 한다. CPU 비율이 보이면 그 비율과 함께 "일부 CPU 오프로딩"으로 기록한다.

### S0-03 컨텍스트 길이별 지연

```
python tools/stage0/bench_llm.py --api ollama --model <모델 이름> --experiments ctx --repeats 5
```

- 대화 원문 1천·6천·1만 2천·2만 4천 자를 넣어 첫 토큰 시간과 전체 생성 시간을 잰다. 매 요청 시스템 프롬프트 첫 줄을 바꿔 프리픽스 캐시를 비운다.
- 실제 토큰 수는 결과의 `promptTokens`로 확인한다. 16K 토큰을 넘으면 `--ctx-chars`를 줄여 다시 잰다.
- Ollama는 `num_ctx`보다 긴 입력을 알리지 않고 자른다. 결과에 `warning`이 찍히면 그 행은 무효로 본다.
- 생성 길이는 150토큰(`--max-tokens`)으로 고정한다.

### S0-04 프리픽스 캐시

```
python tools/stage0/bench_llm.py --api ollama --model <모델 이름> --experiments prefix --repeats 5
```

- 같은 시스템 프롬프트와 대화 원문을 두고 마지막 사용자 대사만 바꿔 네 번 보낸다. 첫 번째(cold)와 나머지(warm)의 첫 토큰 시간을 비교한다.
- warm에서 `enginePromptMs`(엔진의 프롬프트 처리 시간)가 크게 줄면 캐시가 동작한 것이다. Ollama는 캐시가 맞아도 `promptTokens`를 전체 길이로 준다. 줄지 않으면 "캐시 미동작"으로 기록하고 엔진 설정을 확인한다.

### S0-05 판정 병렬 vs 순차

```
# 병렬 슬롯 1개. Ollama는 엔진을 OLLAMA_NUM_PARALLEL=1로 띄운다(기본값은 버전마다 다를 수 있다)
python tools/stage0/bench_llm.py --api ollama --model <모델 이름> --experiments judge --repeats 10 --note "NUM_PARALLEL=1"

# 병렬 슬롯 2개. Ollama는 엔진을 OLLAMA_NUM_PARALLEL=2로 다시 띄운다
python tools/stage0/bench_llm.py --api ollama --model <모델 이름> --experiments judge --repeats 10 --note "NUM_PARALLEL=2"
```

- 판정기와 그림자는 같은 모델을 쓴다(CLAUDE.md 1절). 판정기 쪽은 온도 0, 생성 120토큰 이하다.
- `releaseMs`는 그림자 응답을 내보낼 수 있게 되는 시점이다. 판정이 통과하고 출력 금지 사전 검사(전체 문장이 필요함)가 끝나야 하므로, 순차·병렬 모두 두 요청이 다 끝난 시각으로 잰다.
- 함께 기록하는 값은 다음과 같다.
  - `judgeTotalMs`: 판정 시간 초과(3초 [가설])를 정하는 근거
  - `judgeJsonValid`: 대역 프롬프트에서 JSON이 나왔는지. 판정 품질이 아니라 출력 형식이 안정적인지만 본다
- 슬롯 1개에서 병렬은 엔진 안에서 줄을 서므로 순차와 비슷하게 나올 수 있다. 두 설정을 모두 재야 비교가 된다.
- 판단: 슬롯 2개 설정의 VRAM(S0-02)과 `releaseMs` p90을 함께 보고 고른다. 결과는 TRD 5.2의 판정 방식 기본값과 D-T 결정 기록에 반영한다(사용자 승인 뒤).

### S0-06 생성 취소·로깅 끄기 (수동)

- 생성 취소: 긴 생성(500토큰)을 요청하고 1초 뒤 연결을 끊는다. 엔진 로그나 GPU 사용률로 생성이 멈췄는지 확인한다. 멈추지 않아도 버퍼를 버리므로 출력은 0건이지만(TRD 5.2), GPU 점유가 길어지는지는 기록한다.
- 로깅: 엔진이 프롬프트·응답 본문을 로그나 디스크에 쓰는지 확인한다. 쓰면 끄는 설정을 찾아 기록한다. 끌 수 없으면 실패로 기록하고 6절에서 대안을 고른다.

### S0-07~S0-09 (미준비)

판정기·그림자 시험 프롬프트가 있어야 한다. 시험 프롬프트는 제품 프롬프트(1단계)와 구분해 0단계 실험용 초안으로만 만든다. 그 뒤 다음 순서로 한다.

- S0-07: `eval/crisis/crisis_set.jsonl` 전체를 두 조건(직전 그림자 대사 포함·제외)으로 판정해 등급별 누락 건수를 비교한다. L3 과소 판정은 eval/README의 게이트 기준을 따른다.
- S0-08: 골든 시나리오에서 상황별 2건씩(8건)을 돌려 루브릭으로 채점한다. 벤치마크 점수만으로 품질을 판단하지 않는다(CLAUDE.md 6절). 채점은 사람이 한다.
- S0-09: S0-08 프롬프트로 100턴을 이어 가며 10턴마다 지연과 VRAM, 규칙 유지 여부를 기록한다.

### S0-10 STT·TTS (절차만)

- 한국어 STT 후보 2~3개, TTS 후보 2~3개를 고른다(온프레미스 구동, 라이선스 확인 가능, AMD에서 돌거나 CPU로 쓸 수 있을 것).
- 같은 대본(가상의 대사 20문장)을 쓴다. STT는 미리 녹음한 운영자 본인 음성으로, TTS는 같은 문장으로 잰다.
- 기록: STT 지연(발화 끝 → 전사 완료), 오류 문장 수, TTS 첫 음성 시간, LLM과 함께 적재했을 때의 VRAM.
- 녹음 파일은 측정 뒤 지운다. 저장소에 넣지 않는다.

### S0-11 표정 분석 GPU 공유 (절차만)

- 브라우저에서 표정 분석(예: MediaPipe Face Landmarker)을 켠 상태와 끈 상태로 S0-05를 한 번씩 더 잰다. 차이를 기록한다.
- 영상은 저장하지 않는다.

### S0-12 페이지 파일 잔존 (절차만)

- 측정 방법을 먼저 정해야 한다(예: 가상의 표식 문자열을 메모리에만 두었다가 최대 절전 뒤 `hiberfil.sys`·`pagefile.sys`에서 검색). 방법은 사용자와 정한 뒤 진행한다.

### S0-13 라이선스 원문

- EXAONE 3.5 라이선스 원문을 내려받아 이용·배포·표시 조건을 요약한다. 출처 URL과 확인 날짜를 적는다.
- STT·TTS·표정 모델과 서빙 엔진의 라이선스도 같은 표에 적는다.

## 5. 결과 파일

- `bench_llm.py`는 `tools/stage0/results/llm-<시각>.jsonl`에 한 줄씩 쓴다.
  - 첫 줄(`experiment: meta`): 실행 인자와 환경
  - 마지막 줄(`experiment: vram`): 측정 직후 VRAM. nvidia-smi와 `ollama ps` 출력만 자동으로 받는다
- 생성 문장은 저장하지 않는다. 글자 수(`textChars`)만 남긴다.
- 실행이 끝나면 화면에 p50·p90 표를 출력한다. 보고서에는 이 표와 결과 파일 이름을 함께 적는다.

## 6. 실패 시 대안 (검토 순서)

| 문제 | 먼저 볼 대안 |
| --- | --- |
| RX 9070 XT에서 엔진이 GPU를 쓰지 못함 | 다른 백엔드(Vulkan ↔ ROCm) → 다른 엔진 |
| VRAM 부족 | 컨텍스트 축소 → 병렬 슬롯 1개(순차 판정) → 더 낮은 양자화(품질 재확인 필요) → STT·TTS를 CPU로 |
| 첫 토큰이 김 | 프리픽스 캐시 동작 확인 → 프롬프트 축소(요약 길이 상한) |
| 판정이 3초를 넘음 | 판정 출력 길이 줄이기 → 판정 시간 초과 값 조정(사용자 승인) |
| 엔진이 본문을 로그로 남기고 끌 수 없음 | 다른 엔진 |
